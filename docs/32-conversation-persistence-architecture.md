# Conversation Persistence and Session Architecture\n\n**Status:** Approved architecture; implementation in progress\n**Decision date:** 9 November 2026\n**Scope:** SaviraCortex FastAPI backend, LangGraph RAG workflow, PostgreSQL persistence, and Next.js chat UI.\n\nThis document records the agreed design for server-managed conversations. It is the implementation reference for this feature. Existing source code remains authoritative for current behavior until each phase is implemented and verified.\n\n## 1. Goals\n\n- Stop sending conversation history from the frontend on every generation request.\n- Make the backend the authority for conversation/session ID creation and ownership.\n- Persist complete LangGraph execution state in PostgreSQL using the LangGraph Postgres checkpointer.\n- Provide a first-party conversation list and paginated message-history API.\n- Restore an existing conversation from its persisted graph state.\n- Enforce organization and user ownership on every conversation operation.\n- Keep the initial implementation focused on conversation persistence; add cross-session long-term memory separately.\n\n## 2. Responsibility boundaries\n\n| Component | Responsibility |\n|---|---|\n| Frontend | Send the new message and optional existing conversation ID; keep the returned ID in the route; request paginated history |\n| FastAPI backend | Create IDs, authenticate and authorize, manage conversation metadata, coordinate message writes and graph invocation |\n| `conversations` table | Application-level conversation identity, owner, title and timestamps |\n| `conversation_messages` table/read model | Efficient chronological message history and offset pagination for the UI |\n| LangGraph `AsyncPostgresSaver` | Durable graph checkpoints, message state and execution state |\n| Future LangGraph Store | Cross-thread long-term memory partitioned by organization and user |\n\nThe application tables and checkpointer tables have distinct purposes. Do not manually duplicate LangGraph's internal checkpoint schema.\n\n## 3. Identifiers and namespaces\n\n- `organization_id`: tenant boundary, resolved/validated by the backend.\n- `user_id`: authenticated SaviraCortex user, resolved by the backend.\n- `conversation_id`: UUID generated by the backend and stored as `conversations.id`.\n- LangGraph `thread_id`: exactly the string representation of `conversation_id`.\n- LangGraph `checkpoint_ns`: leave at the default for the top-level graph unless actual subgraph isolation requires a namespace.\n- Future Store namespace: `(str(organization_id), str(user_id))`.\n\nDo not use client-supplied user or organization IDs as authorization evidence. Do not overload `checkpoint_ns` with tenant/user identifiers. The backend must verify conversation ownership and organization membership before loading or mutating graph state.\n\nExample graph config:\n\n```python\nconfig = {\n    "configurable": {\n        "thread_id": str(conversation_id),\n    }\n}\n```\n\n## 4. PostgreSQL data model\n\n### 4.1 Application-owned conversations table\n\nProposed fields:\n\n| Field | Type | Notes |\n|---|---|---|\n| `id` | UUID | Primary key; generated by backend |\n| `organization_id` | UUID | Organization owner; FK where compatible with current model |\n| `user_id` | UUID | User owner; FK where compatible with current model |\n| `creation_request_id` | UUID, nullable | Unique per organization/user; makes first-turn conversation creation retry-safe |\n| `title` | VARCHAR | Generated from first user message; user-editable |\n| `title_is_user_edited` | BOOLEAN | Prevents asynchronous title generation from overwriting a user rename |\n| `title_generated` | BOOLEAN | Prevents repeated background title updates |\n| `next_sequence` | BIGINT | Atomically allocates stable message ordering within a conversation |\n| `created_at` | TIMESTAMP WITH TIME ZONE | Creation timestamp |\n| `updated_at` | TIMESTAMP WITH TIME ZONE | Updated on successful message activity and title changes |\n\nAdd an index supporting the common listing query, e.g. `(organization_id, user_id, updated_at DESC)`, and a unique constraint on `(organization_id, user_id, creation_request_id)`. Follow existing model conventions for UUIDs, timestamps, naming, and constraints. Conversation and message tables are created idempotently during FastAPI lifespan startup; the checkpointer performs its own setup in the same lifecycle.\n\n### 4.2 Paginated message-history read model\n\nThe chat UI must not fetch the entire message history on open. It loads the newest page, then requests older pages as the user scrolls upward.\n\nLangGraph checkpoints are snapshots of graph state, not a purpose-built offset-paginated message table. Therefore, maintain an application-owned `conversation_messages` read model/projection for UI history. This is not a second graph-state store: the checkpointer remains authoritative for graph execution and resume state; the message table is the query-optimized UI history projection.\n\nProposed fields:\n\n| Field | Type | Notes |\n|---|---|---|\n| `id` | UUID | Message row ID |\n| `conversation_id` | UUID | FK to conversations |\n| `sequence` | BIGINT | Monotonically increasing per conversation; stable ordering |\n| `role` | VARCHAR/enum | `user`, `assistant`, optionally supported system/tool roles if product UI needs them |\n| `content` | TEXT or JSONB | Store the normalized UI-safe message content; choose after inspecting LangChain message shape and current response schema |\n| `created_at` | TIMESTAMP WITH TIME ZONE | Message timestamp |\n| `request_id` / `generation_id` | UUID, nullable | Idempotency/correlation key for retries and generation records |\n\nAdd unique constraints/indexes for `(conversation_id, sequence)`, and an idempotency constraint appropriate to the chosen request ID. The exact schema must follow existing SQLAlchemy and generation-feedback model conventions.\n\nThe backend must write the user and completed assistant message projections consistently with successful graph turns. Use an explicit transaction/reconciliation strategy; do not silently let the projection drift from checkpoint state. Avoid writing every streamed token as a message row. Persist one completed assistant message per turn. Handle failed/interrupted turns and retries explicitly. Stable request IDs are unique per conversation/role; the first request ID is also recorded on the conversation so a retry before the client receives its new conversation ID does not create a second conversation.\n\n## 5. Checkpointer setup and lifecycle\n\n- Add the compatible `langgraph-checkpoint-postgres` package to backend dependencies after checking the installed LangGraph version and lockfile.\n- Initialize one application-lifecycle-managed `AsyncPostgresSaver` using the configured PostgreSQL connection/pool.\n- Run `await checkpointer.setup()` during application startup so LangGraph creates/upgrades its own internal tables.\n- Compile the RAG graph with the checkpointer.\n- Close the saver/pool cleanly during application shutdown.\n- Do not create custom checkpoint/snapshot tables or manually alter LangGraph-owned tables.\n- Do not assume exact internal table names; they are package-version-managed.\n\nThe checkpointer must be shared safely by requests, not created and migrated independently for each generation call.\n\n## 6. Graph state and RAG integration\n\n- Replace frontend-provided history/context as the durable conversation source with a LangGraph state field such as `messages`, using the appropriate LangGraph message reducer (e.g. `add_messages`).\n- On each request, load the conversation's latest checkpoint by `thread_id`, append only the newly submitted user message, execute the existing RAG graph, append the completed assistant response, and let the checkpointer persist state.\n- Adapt retrieval and generation nodes to derive their conversation context from the restored message state.\n- Preserve the existing query processing, authorization, retrieval, reranking, evidence validation, generation, citation and streaming behavior.\n- Do not rewrite the RAG pipeline solely to add persistence.\n- Prevent duplicate user messages on client retries by using a stable request/idempotency key and checking it before appending.\n- Serialize generation turns per conversation with a PostgreSQL advisory lock so concurrent API workers cannot interleave checkpoint writes for the same thread.\n- Streaming should persist the completed assistant answer once, not each token delta. Define how interrupted streams are represented and whether a retry resumes or starts a new turn.\n\n## 7. API contract\n\nUse the existing API conventions and organization-scoped routes where appropriate. Proposed operations:\n\n| Method | Route | Purpose |\n|---|---|---|\n| POST | `/organizations/{organization_id}/conversations` | Optional explicit empty conversation creation if needed by UI |\n| GET | `/organizations/{organization_id}/conversations` | List current user's conversations |\n| GET | `/organizations/{organization_id}/conversations/{conversation_id}` | Get conversation metadata |\n| GET | `/organizations/{organization_id}/conversations/{conversation_id}/messages?limit=20&offset=0` | Return a message page |\n| PATCH | `/organizations/{organization_id}/conversations/{conversation_id}` | Rename conversation |\n| DELETE | `/organizations/{organization_id}/conversations/{conversation_id}` | Delete conversation, messages and checkpoints |\n| POST | Existing generation route | Accept new query plus optional conversation ID; return conversation ID |\n\nExact paths and response envelopes should be aligned with the existing router rather than introducing inconsistent route conventions.\n\nGeneration request shape:\n\n```json\n{\n  "query": "Explain this document",\n  "conversation_id": null,\n  "request_id": "optional-client-generated-idempotency-uuid"\n}\n```\n\nFor an existing chat, send its existing `conversation_id`. The frontend must not send `conversation_history`, previous messages, `user_id`, or an authorization claim.\n\nGeneration response includes `conversation_id` (and existing generation/answer fields). The frontend updates the URL only after it receives the backend-generated ID for the first turn.\n\n## 8. Pagination behavior\n\n- Initial open: fetch the latest 20 messages.\n- Render the page in chronological order.\n- When the user scrolls to the top, fetch the next 20 older messages.\n- Use `limit` and `offset` as requested.\n- Return pagination metadata such as `limit`, `offset`, `has_more`, and optionally `total`.\n- Enforce a maximum page size server-side.\n- Use stable ordering by `sequence` (and a deterministic tie-breaker if needed).\n- Offset pagination can shift when new messages arrive. Keep the newest page anchored and use a consistent query/order strategy; if concurrent insertions make offsets unstable, switch the internal cursor to `before_sequence` while preserving the user-facing older-message pagination behavior. This tradeoff should be tested.\n\n## 9. Conversation creation and title generation\n\n- For a new chat, frontend sends no conversation ID.\n- Backend creates a conversation UUID and metadata record.\n- Backend invokes LangGraph with that UUID as `thread_id`.\n- Backend returns the conversation ID; frontend updates the URL to include it.\n- For an existing chat, backend reuses the supplied ID after authorization; it must not create a new conversation.\n\nTitle policy:\n- Backend generates a concise title from the first user message, ideally around 5–8 words.\n- Generate only once; do not regenerate on every turn.\n- Prefer a lightweight title-generation call that does not block the main RAG response (background execution/queue appropriate to the existing app lifecycle).\n- Set a deterministic fallback from a normalized/truncated first message immediately so a failed title-generation call never leaves a blank title.\n- Allow users to rename titles manually.\n- Ensure title generation is idempotent and cannot overwrite a user-edited title.\n\n## 10. Conversation deletion\n\nDeleting a conversation must remove all associated persisted state:\n\n1. Authenticate the caller and verify organization membership and conversation ownership.\n2. Delete the conversation's LangGraph checkpoint records using the supported checkpointer API for the pinned package version (or a documented, tested cleanup mechanism).\n3. Delete the message-history projection and conversation row.\n4. Ensure retries are safe and partial failures are recoverable.\n\nDo not issue ad hoc SQL against LangGraph internal tables unless the pinned library explicitly requires and documents that mechanism. Since checkpoint storage and application rows may not share one transaction boundary, design deletion as an idempotent cleanup workflow (or a tombstone/status approach) so a failure does not leave an apparently deleted conversation with orphaned checkpoints.\n\n## 11. Security, consistency and operational requirements\n\n- Resolve user identity from the verified Firebase token and existing user/membership services.\n- Check organization membership and conversation ownership on every read, update, generation and delete.\n- Never expose another user's conversation by guessing a UUID.\n- Apply server-side page-size limits and validate offset values.\n- Avoid logging message content or secrets unnecessarily.\n- Make message writes idempotent and handle duplicate requests, including a retry of the first request before a conversation ID has been returned.\n- Keep graph checkpoint and message projection updates consistent; define retry/reconciliation behavior.\n- Serialize simultaneous requests on the same conversation with a PostgreSQL advisory lock shared across API worker processes.\n- Keep database connections and checkpointer resources within FastAPI lifespan.\n- Follow existing project policy for schema changes and database setup; do not run destructive reset scripts without explicit approval.\n\n## 12. Implementation phases\n\n### Phase 1 — persistent conversations\n\n1. This is separate from Phase 1 conversation persistence and is not required for initial session restoration.\n\n## 13. Acceptance criteria\n\n- A new conversation ID is generated by the backend, never by the frontend.\n- A successful first response returns the ID and the frontend updates the URL.\n- A request with an existing ID resumes the same LangGraph thread after ownership checks.\n- Frontend generation requests contain only the new query, optional conversation ID and idempotency metadata; no conversation history.\n- Graph messages and state survive backend restarts.\n- Conversation listing is organization/user scoped.\n- Opening a conversation fetches only the latest 20 messages.\n- Scrolling upward retrieves older messages in stable chronological order.\n- Conversation title is generated once from the first user message, with fallback and rename support.\n- Deleting a conversation also deletes its checkpoint state and message projection, with safe retry behavior.\n- Existing RAG retrieval, authorization, citation validation and streaming behavior remain intact.\n- Tests cover ownership violations, pagination, retries/idempotency, graph resume, title generation, deletion cleanup and frontend URL/history behavior.\n\n---\n\n## 14. Database initialization and runtime notes\n\n- FastAPI lifespan creates the application-owned conversation tables if absent and initializes the shared LangGraph saver. Shutdown closes both the async psycopg pool and SQLAlchemy engine.\n- Startup uses additive DDL only for the existing conversation schema: if the `conversations` table already exists, add `creation_request_id UUID` if absent and create its unique owner/request index if absent. Do not drop or recreate existing conversation/message tables.\n- The live database may contain the application tables before this feature is deployed; startup must be safe on both fresh and existing schemas.\n- On Windows, configure `WindowsSelectorEventLoopPolicy` before the async application loop is created because psycopg async connections do not support the default Proactor loop.\n- Verify the checkpointer against the real PostgreSQL database with a temporary thread: write, restore, update, and delete it. The temporary test thread must be deleted after verification.\n\n\n## 15. Phase 2 — PostgreSQL cross-thread memory implementation\n\nThe first implementation of Phase 2 uses LangGraph's asynchronous PostgreSQL Store from the already-pinned `langgraph-checkpoint-postgres` package (3.2.0). It shares the application-lifecycle-managed psycopg connection pool with `AsyncPostgresSaver`; no second database or application-owned memory table is introduced.\n\n- Store namespace is exactly `(str(organization_id), str(user_id))`. Both values are resolved by the authenticated backend; the client cannot choose a memory namespace.\n- Store vector indexing uses the active application embedding provider and its configured dimensions, indexing only the `text` field. This keeps Jina/Cloudflare provider selection consistent with the RAG stack.\n- The graph retrieves up to five semantically relevant memories for the current query before document retrieval. Memory lookup failure is fail-open: the request continues without memory context.\n- Generation receives the memory values in a distinct prompt section. System instructions explicitly limit memory to personalization and context resolution; only authorized retrieved company-document evidence can support factual company-policy claims or citations.\n- After a successful, validated turn, a small extraction call examines only the user's current message. It stores explicit durable preferences, profile/work context and project facts; it excludes one-off requests, document-derived facts, guesses, credentials and highly sensitive personal data. Stable subject keys upsert changed facts across conversations.\n- A per-turn Store marker keyed by request ID makes extraction idempotent. Fact values retain their source conversation ID and update timestamp. The marker is written after all fact writes so an interrupted write can be retried.\n- The Store is initialized and closed with FastAPI lifespan alongside the checkpointer. LangGraph owns the Store schema and migrations; do not create or edit its internal tables manually.\n\nThis phase intentionally does not add a separate user-facing memory-management UI or memory CRUD API. Those can be added independently without changing the namespace or storage model.\n\n### Phase 2 verification record (9 November 2026)\n\n- Live PostgreSQL Store schema setup, `aput`, `aget`, semantic `asearch`, and `adelete` passed.\n- Live extraction using a synthetic preference, semantic retrieval in the same organization/user namespace, and cleanup passed.\n- A Store fact remained readable and searchable after closing and reopening the shared PostgreSQL pool; cleanup passed.\n- Focused Phase 2, generation prompt, graph and persistent-generation tests: 19 passed.\n- Full backend suite: 467 passed, 9 known unrelated baseline failures, 15 deselected.
